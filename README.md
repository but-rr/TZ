# Техническое задание: AI-платформа генерации контента

> **Статус:** предварительное ТЗ  
> **Ориентир:** платформа по типу [Avalava](https://avalava.ai/), но с собственными дизайном, кодом и продуктовой логикой.  
> **Цель:** запустить коммерчески пригодный MVP, без преждевременного усложнения инфраструктуры.

---
## 1. Основные решения

- **Архитектура:** модульный монолит, отдельный процесс обработки фоновых задач (worker), одна кодовая база/monorepo.
- **Размещение:** один VPS для приложения, API, PostgreSQL, Redis и worker на старте; файлы и резервные копии — **вне VPS**.
- **Генерация:** внешние AI API.
- **Монетизация:** кредиты с журналом операций; разовое пополнение + подписки, с выдачей определенного количества токенов.
- **Разработка:**  автономные модули, тесты и контролируемые изменения. Разработка сайта как витрины + Разработка сайта приложения (app.) + Разработка сайта под Telegram MiniApps (app.)

## 2. Технологический стек

| Слой | Рекомендуемая технология | Примечание |
|:---|:---|:---|
| **Frontend** | Next.js + React + TypeScript | SSR/SEO для публичных страниц, клиентские интерфейсы для кабинета |
| **UI** | Tailwind CSS + shadcn/ui | Единая дизайн-система, адаптивная вёрстка |
| **Backend** | NestJS + TypeScript | Модульный монолит; **Fastify — после проверки совместимости авторизации**, иначе стандартный адаптер NestJS |
| **База данных** | PostgreSQL + Prisma | Транзакции и миграции схемы; индексы по реальным запросам |
| **Фоновые задачи** | Redis + BullMQ | Очереди, повторы, лимиты, распределение обработки |
| **Файлы** | S3-compatible Object Storage | Прямые загрузки по signed URL; приватные объекты, временные ссылки на скачивание |
| **Авторизация** | Better Auth **после интеграционного теста** или готовые механизмы NestJS | Не писать собственную криптографию/хеширование/управление сессиями с нуля |
| **Reverse proxy / HTTPS** | Caddy **+** Nginx | Caddy проще для автоматического TLS |
| **Контейнеризация** | Docker Compose | Без Kubernetes и микросервисов на MVP |
| **Мониторинг** | Sentry + Uptime Kuma | Ошибки, доступность, очередь, БД. |
| **CI/CD** | GitHub Actions | Линтер, типы, тесты, сборка, миграции, выкладка |
| **Нагрузочное тестирование** | k6 | Отдельно HTTP-нагрузка и моделирование очереди генераций |
| **Пакетный менеджер** | pnpm workspaces | Monorepo с общими типами и схемами валидации |

## 3. Функционал MVP

### 3.1. Пользователи и авторизация

- [ ] Регистрация и вход (минимум email + пароль; OAuth — пока что два варианта (Telegram + Google) - это для сайта). В MiniApps авторизация автоматическая.
- [ ] Профиль, управление учётной записью.
- [ ] Баланс кредитов, история операций и история генераций.
- [ ] Роли **user / admin**; проверка прав доступа на backend.
- [ ] Защита авторизации от перебора и массовой регистрации.
- [ ] Выбор типа генерации и модели.
- [ ] Текстовый промпт и параметры модели (размер, соотношение сторон, длительность и т. д. — если поддерживаются API).
- [ ] Загрузка исходного изображения для редактирования/анимации.
- [ ] Отображение предварительной стоимости в кредитах **до запуска**.
- [ ] Создание задачи и получение `generationId` без ожидания окончания генерации в HTTP-запросе.
- [ ] Статусы: `queued`, `submitting`, `processing`, `completed`, `failed`, `cancelled` (где применимо).
- [ ] История запросов и результатов; предпросмотр и скачивание файла.
- [ ] Понятные сообщения об ошибках; повторная отправка только без двойного списания.
- [ ] Ограничения на размер/тип входных файлов, максимальное число активных задач.

### 3.3. Кредиты и платежи

- [ ] Пакеты кредитов и тарифы; цены на каждую модель/режим.
- [ ] **Журнал кредитных операций** (`credit_ledger`), а не только изменяемое поле `balance`.
- [ ] При запуске генерации — **резервирование** кредитов в транзакции.
- [ ] После успешного выполнения — окончательное списание; при подтверждённой неудаче — возврат резерва.
- [ ] При таймауте и неизвестном результате — сверка состояния у AI-провайдера до возврата средств.
- [ ] Защита от повторных webhook, повторных задач, повторного зачисления и гонок запросов.
- [ ] Подключение **одного** платёжного провайдера (Пример: Юкаssа).
- [ ] Пополнение баланса, история платежей, успешные/неуспешные оплаты, обработка возвратов.
- [ ] Вся финансовая логика и подтверждение оплаты выполняются на backend.

### 3.4. Минимальная админка

- [ ] Поиск пользователей, роли, блокировка и просмотр истории операций.
- [ ] Просмотр генераций, ошибок, статусов очередей, ID задач провайдера.
- [ ] Включение/отключение моделей, настройка цены в кредитах и лимитов.
- [ ] Просмотр затрат по провайдеру/модели и агрегированной выручки (при наличии платёжных данных).
- [ ] Безопасная ручная корректировка кредитов **только через журнал с причиной**.
- [ ] Audit log действий администратора.

### 3.5. Минимальные публичные страницы

- [ ] Главная / лендинг и описание возможностей.
- [ ] Страницы входа/регистрации, генератора, тарифов, личного кабинета.
- [ ] Условия использования, политика конфиденциальности, контакты/поддержка.
- [ ] Адаптивность для мобильных устройств.

## 4. Первые 3–5 AI-моделей / режимов

| Приоритет | Режим | Входные данные | Результат
|:---:|:---|:---|:---
| **P0** | Text → Image | Промпт + параметры | Изображение
| **P0** | Image → Image / Edit | Изображение + промпт | Изменённое изображение
| **P0** | Text → Video | Промпт + параметры | Видео
| **P1** | Image → Video | Изображение + промпт | Анимированное видео
| **P1** | Text → Speech | Текст | Аудио

**Важно:** в исходном списке есть генерация аудио, но выбранные 3–4 режима покрывают только фото/видео. Если **аудио — обещанная функция первого релиза**, пятым режимом сделать Text → Speech. Если нет — перенести аудио на следующий этап.

## 5. Жизненный цикл генерации

```text
Пользователь
    |
    v
Frontend -> Backend: проверка тарифа, лимитов и входных данных
    |
    v
PostgreSQL: создание Generation + резерв кредитов (одна транзакция)
    |
    v
Redis / BullMQ: постановка короткой задачи на отправку
    |
    v
Worker -> AI API: создание внешней задачи
    |
    v
PostgreSQL: сохранить providerJobId и статус processing
    |
    v
Webhook провайдера / периодическая сверка (polling)
    |
    +-- success --> сохранить результат в S3 --> завершить списание
    |
    +-- confirmed failure --> failed --> освободить резерв
    |
    +-- unknown / timeout --> reconciliation, без поспешного возврата
    |
    v
Frontend: обновление статуса и показ результата
```

**Требования к обработке:**

1. Не держать HTTP-соединение или слот worker открытым на всё время генерации у внешнего провайдера.
2. Обрабатывать webhook **идемпотентно**, с проверкой подлинности и защитой от повторов.
3. У задач — уникальные идентификаторы; резерв, списание и возврат не могут выполняться дважды.
4. Retry только для временных ошибок, с backoff; для необратимых ошибок — остановка и фиксация причины.
5. Предусмотреть очередь сверки «зависших» задач: внешняя генерация могла завершиться, пока webhook был недоступен.
6. Ограничить число параллельных запросов и расход бюджета **по каждому AI-провайдеру**.
7. PostgreSQL — источник истины по генерациям и деньгам; Redis не является долговременным учётом баланса.
8. Установить правила хранения и очистки результатов, входных файлов и записей очередей.

## 6. Хранение файлов

- Пользователь загружает файлы **напрямую в бота или на сайте, которые после этого попадают в S3-compatible storage** по временной подписанной ссылке (signed upload URL). Удаление этих временных файлов с vps каждый день. (Они остаются только в базе S3)
- Backend выдаёт ссылку после проверки прав, размера, квот, типа и назначения загрузки; после загрузки отдельно проверяет фактический файл.
- Приватные исходники не делать общедоступными по постоянным URL.
- Результаты отдавать через временные подписанные ссылки/CDN с правилами доступа.
- Для видео не пропускать весь поток скачивания через NestJS или диск VPS.
- Утвердить лимиты объёма, срок хранения, стоимость хранилища и исходящего трафика.
- Исключить выполнение произвольных файлов; проверять MIME, формат и размер; предусмотреть санитарную обработку метаданных при необходимости.

## 8. Сервер и эксплуатация

### Стартовая конфигурация (приблизительно)

| Ресурс | План | Комментарий |
|:---|:---|:---|
| CPU | **8 vCPU** | Рабочая гипотеза; зависит от качества выделенных CPU |
| RAM | **16 GB** | Учесть лимиты контейнеров, память PostgreSQL/Redis и пиковые задачи |
| SSD | **160–200 GB NVMe** | Допустимо, но при выносе всех медиа в S3 может хватить меньшего диска |
| Сеть | **1 Gbit/s порт** | Проверить реальные квоты трафика, а не только скорость порта |

Обязательные операции:

- [ ] Docker healthchecks, автоматический перезапуск контейнеров, безопасное обновление приложения.
- [ ] CI/CD: typecheck, lint, unit/integration tests, сборка, ручное подтверждение production-деплоя.
- [ ] Миграции БД через проверяемый процесс деплоя, с планом отката.
- [ ] Резервные копии PostgreSQL **вне VPS**, регулярная проверка восстановления.
- [ ] Мониторинг CPU, RAM, диска, ошибок, очередей, задержек API, количества/длительности генераций.
- [ ] Алерты по переполнению очереди, отказу БД, ошибкам платежей и перерасходу бюджета AI API.
- [ ] Ограничение размера логов, retention для Redis/BullMQ и медиа.
- [ ] WAF/anti-bot/rate limiting на входе; firewall, закрытые порты БД и Redis.

## 9. Нагрузочное тестирование

Инструмент: **k6**. Тестировать не только «сколько людей откроют сайт», но и **скорость создания задач и рост очереди**.

| Сценарий | Что проверяем |
|:---|:---|
| Просмотр главной, тарифов и кабинета | Скорость отдачи страниц, кэш, CDN |
| Авторизация и получение баланса | Задержки API, нагрузка PostgreSQL |
| Массовая постановка генераций | Транзакции резервирования, Redis, rate limiting |
| Всплеск после рекламного перехода | Ошибки HTTP, память, стабильность процессов |
| Отказ / таймаут AI-провайдера | Retry, reconciliation, отсутствие потерь задач |
| Повторный webhook / оплата | Отсутствие двойных зачислений и списаний |

## 10. Безопасность, данные и бюджет

- **Антифрод:** защита бонусов, мультиаккаунтов, платежей, скачиваний; ограничения по IP/аккаунту/дню.
- **Контент:** правила допустимых запросов и изображений, действия при нарушениях, политика AI-провайдеров.
- **Бюджет:** лимит расходов за день/месяц, стоимость по каждой модели, стоп-сигнал при исчерпании бюджета и оповещения.
- **Ценообразование:** учесть себестоимость AI API, число повторных/неудачных генераций, хранение, исходящий трафик, эквайринг и налоги. Цены кредитов не задаются навсегда в коде.
- **Поддержка:** идентификатор каждой генерации/платежа, чтобы можно было быстро разобраться с обращением.

## 11. Критерии готовности MVP

MVP считается готовым к публичному запуску, если:

- [ ] Пользователь может зарегистрироваться, пополнить баланс и увидеть подтверждённую транзакцию.
- [ ] Не менее трёх выбранных режимов генерации стабильно работают через внешние API.
- [ ] Для успешной, неуспешной, повторной и «зависшей» задачи баланс остаётся корректным.
- [ ] Результаты хранятся вне VPS и доступны владельцу в личном кабинете.
- [ ] Администратор может посмотреть историю, отключить проблемную модель и ограничить расходы.
- [ ] Настроены бэкапы **с проверенным восстановлением**, мониторинг и критические уведомления.
- [ ] Пройдены согласованные нагрузочные и интеграционные тесты.
- [ ] Пройден базовый security-review: права доступа, платежи, загрузки, webhook, rate limits.
